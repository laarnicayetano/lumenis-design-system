# `_ds_manifest.json` — what it is and how it's built

This file is generated by Claude Design's own scanner (`"source": "spa"`), not
hand-written. Nothing in this repo currently regenerates it — it's a snapshot
from whenever Claude Design last scanned the project. This doc reverse-engineers
its schema from the current file plus the conventions it clearly keys off in
source, so we have a shared reference before touching anything structural.

## Top-level shape

```
{
  namespace: string,          // "LumenisDesignSystem_<id>" — matches the claude.ai/design project id
  components: Component[],
  startingPoints: [],         // empty in the current snapshot — purpose unconfirmed
  cards: Card[],
  templates: Template[],
  hasThumbnailHtml: boolean,  // true — thumbnail.html exists at repo root
  globalCssPaths: string[],   // every stylesheet loaded globally, in order
  tokens: Token[],
  themes: Theme[],
  fonts: Font[],
  brandFonts: BrandFont[],
  source: "spa"
}
```

## Sections and what they scan

| Section | Scanned from | Convention it keys off |
|---|---|---|
| `globalCssPaths` | `styles.css` | The literal `@import` list, in order |
| `tokens` | `tokens/*.css` | Every CSS custom property (`--name: value`). `kind` defaults to inferred type (`color` for hex/rgb/var, else `other`); an inline `/* @kind color */` or `/* @kind other */` comment overrides the guess — see `tokens/surfaces.css` and `tokens/typography.css` for examples (gradients, easing values, uppercase keywords). `definedIn` is the file path. |
| `themes` | `tokens/subbrands.css` | Every `[data-subbrand="..."]` selector, labeled from the selector value |
| `fonts` | `tokens/fonts.css` | Every `@font-face` rule — family, weight, style, and the `url(...)` file paths referenced |
| `brandFonts` | same, cross-referenced against `--font-*` token usage | `status: "ok"` if the font-family is actually wired to a token; which tokens use it |
| `components` | **file existence under `components/**`, one entry per named export** | `sourcePath` — **currently wrong**: lists `.jsx` for every entry (e.g. `components/actions/Button/Button.jsx`) though the real files have been `.tsx` since before this session touched anything. Predates our work; not something we introduced. |
| `cards` | **`.card.html` files containing an `@dsCard` HTML comment** | `<!-- @dsCard group="..." viewport="WxH" name="..." subtitle="..." -->` as the first line. **This is now stale** — guidelines/component specimens are `.tsx` as of this session, so no `.card.html` source exists for the scanner to find. The 38 entries currently in the manifest are a snapshot from before that conversion. |
| `templates` | `templates/**/*.dc.html` | One entry per Claude Design canvas template — `name`/`description` from inside the file, `thumbnail.path` pointing at a `.thumbnail` capture folder |

## What this means practically

- **Tokens/colors/fonts/themes are unaffected** by anything done this session — that layer of the manifest is still accurate, because `tokens/*.css` and `styles.css` weren't touched.
- **`cards` is the one section broken by the guidelines/specimen `.tsx` conversion.** A fresh scan today would very likely find 0 cards, not 38 — the convention it looks for (`@dsCard` comment in a `.card.html` file) doesn't exist in source anymore.
- **`components[].sourcePath` using `.jsx` predates this session** — components have been `.tsx` all along, so this was already stale before any of today's changes. Whether it's actually load-bearing (does Claude Design's live preview read `sourcePath` directly, or is it just a "view source" deep link, with rendering actually happening off a compiled bundle?) is unconfirmed — worth checking directly in Claude Design rather than assuming from the manifest alone.

## Open questions (unconfirmed — worth testing in Claude Design directly before architecting around them)

1. Does Claude Design require `cards`/`components` source files to be **committed to git**, or does its sync just need them present in the working tree at scan time? The fact that `cards[].path` points at repo-relative source paths (not a `dist/` build output path) suggests committed-in-source, but this isn't confirmed.
2. Is `_ds_manifest.json` **overwritten by Claude Design on its own sync**? If so, any manual fix or regeneration from this repo's own build would be undone the next time someone opens the project in Claude Design — meaning durability of a fix depends on Claude Design itself learning to scan whatever new convention we adopt, not on us alone.
3. Is a stale/wrong `sourcePath` or missing `cards` entry **cosmetic** (e.g. a broken "view source" link, a missing preview thumbnail) or does it **break loading entirely**? The `.jsx`-vs-`.tsx` mismatch already existing for components without apparent issue suggests some slack in the system, but that's inference, not confirmation.
