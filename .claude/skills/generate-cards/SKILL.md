# Generate @dsCard shims for specimen sources

Claude Design's scanner only recognises a card as `<!-- @dsCard … -->` on the
**first line of an `.html` file in the working tree**. `scripts/build.ts`
already emits exactly that comment (via `dsCardComment()`), but writes it to
`dist/`, which is gitignored and never scanned. So every guideline and
component specimen — real `.tsx` source, SSR'd at build time — is invisible
in the Design System tab even though it's perfectly built for GitHub Pages.

This skill closes that gap by generating the same shim **next to each
specimen source** (`guidelines/*.tsx`, `components/*/*.specimen.tsx`).
Metadata stays single-sourced in the `.tsx`; the `.html` is generated,
committed, and never hand-edited.

## When to use this

- After adding or removing a `guidelines/*.tsx` or `components/*/*.specimen.tsx` file.
- After changing a specimen's `card` metadata (group, viewport, name, subtitle) or renaming its default-exported function.
- Whenever `git diff` shows a generated `*.card.html` going stale next to a specimen you just edited.

## Running it

```
node .claude/skills/generate-cards/generate-cards.ts
```

Run from the repo root (it resolves the root relative to its own file path,
so it doesn't depend on `cwd`). It:

1. Walks `guidelines/*.tsx` and `components/*/*.specimen.tsx`.
2. Bundles each one standalone with esbuild (same approach as `scripts/build.ts`'s `importSpecimenModule` — a temp `.mjs` written inside the repo so bare `import 'react'` resolves) and imports it to read its metadata.
3. Resolves the card metadata **structurally** — either a `card` export or a single `<Name>Card` export — rather than assuming one fixed name, so this keeps working if that convention ever changes.
4. Writes a minimal HTML shim next to the source: the `@dsCard` comment, then a page that loads `_ds_bundle.js` and mounts `NS.<ExportName>` off whichever global starts with `LumenisDesignSystem` (resolved by prefix, not hardcoded, so a fork of this system doesn't break the script).
5. Deletes any `*.card.html` whose specimen source no longer exists, so renames/removals don't leave orphans.

Commit the generated `.card.html` files — they're build input for Claude Design's scanner, not build output; `dist/` remains the separate, from-scratch SSR path for GitHub Pages and the two never collide.

## Notes

- **`.card.html` next to specimen source is not a `scripts/build.ts` input.** `build.ts`'s `collectDsCards()` only scans `ui_kits/`, so it won't pick these up and double-render them. If that ever changes to also scan `guidelines/`/`components/`, exclude the generated files or every specimen will be counted twice.
- **Claude Design sweeps every `.ts`/`.tsx` in the tree into its own bundle**, and `node:`/esbuild imports break that transform — the same reason `scripts/build.ts` isn't synced into the Claude Design project. This script has the same imports and the same constraint: it runs on your machine or in CI, and stays out of the Claude Design working tree (only its generated `.html` output is meant to be seen there).
- **Optional CI drift check** — since the output is committed, a stale shim is a reviewable diff:
  ```yaml
  - run: node .claude/skills/generate-cards/generate-cards.ts
  - run: git diff --exit-code || (echo "Card shims are stale — rerun the generate-cards skill" && exit 1)
  ```
- The `_ds_bundle.js` reference in each shim is the same file `templates/*/ds-base.js` already depends on — generated by Claude Design's own scanner, not by this repo's build, and not committed here (see `.gitignore`). Whether Claude Design serves it to these shims without it being committed is the same open question already flagged for the templates; verify in Claude Design directly rather than assuming, per this repo's `CLAUDE.md`.
