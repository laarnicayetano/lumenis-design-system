# design-sync notes

- SplitLayout: story used JSX in module-scope `args` without importing React (tsconfig has `"jsx": "react"`, classic runtime) -> storybook build threw `React is not defined` (sb-error). Fix: add `import React from "react";` to `SplitLayout.stories.tsx`. Not global — other stories either don't use module-scope JSX or already import React (e.g. Tabs).
- Badge: Inverse story's decorator wrapper renders full-bleed in the preview vs snug/centered in storybook -> storybook's meta-level `parameters.layout: "centered"` shrinks the canvas to fit content, which the preview harness doesn't replicate. Framing only — the component itself is pixel-identical. Not fixed, not actionable (harness framing difference, not a component defect).
- [GENERAL] `.ds-sync/storybook/http-serve.mjs`'s MIME table lacked `.svg` (and other non-html/js/css/json/png types), defaulting to `application/octet-stream` — Chromium refuses to decode `<img src="*.svg">` under that MIME type, so BOTH the storybook reference and the preview panel showed broken images identically, masking real fidelity. This is a bug in the skill's own shared script, not a per-repo issue (it isn't wired for `cfg.libOverrides`) — patched locally this run by adding `.svg`, `.jpg/.jpeg`, `.gif`, `.webp`, `.woff2/.woff`, `.otf`, `.ttf` to the MIME table. **This fix does not persist**: `.ds-sync/` is re-copied fresh from the skill's bundled scripts on every sync, so re-apply it (or check if a newer skill version has fixed it upstream) on the next sync if any component with an `<img src="*.svg">` shows broken images on both sides again.
- Logotype: `assetBase` defaults to a *relative* `"assets"` path, resolved against the consuming page's own URL. The story overrides it to `/foundations/assets` for Storybook's `staticDirs` mapping (see `.storybook/main.ts`) — but that path doesn't exist in a shipped design-system project, so the storybook-derived preview would 404 in production too. Fix: owned `.design-sync/previews/Logotype.tsx` explicitly sets `Logotype.assetBase = "../../../assets"` (the correct relative depth from `components/Brand/Logotype/Logotype.html` to the project root, where `assets/logo/*.svg` actually lives in the uploaded project). Any other component whose card nests at the same `components/<group>/<Name>/` depth and loads assets via a page-relative path needs the same treatment — check before assuming a generated preview "just works" for asset-loading components.

- SiteFooter and SiteHeader both render `<Logotype .../>` internally without setting `assetBase`. Logotype's default (`"assets"`, relative) resolves against the *consuming card's own URL* — for these two it's `components/Navigation/SiteFooter|SiteHeader/*.html`, 3 levels below the project root where `assets/logo/*.svg` actually lives. This is broken in the **real storybook too** (not a design-sync artifact) since the story doesn't override it there either. Fix: owned `.design-sync/previews/SiteFooter.tsx` and `.design-sync/previews/SiteHeader.tsx`, each setting `Logotype.assetBase = "../../../assets"` before render (same fix as `.design-sync/previews/Logotype.tsx`, but must be repeated per card — the override doesn't carry across standalone card pages). Confirmed the override compiles into the shipped bundle (`ds_exports.Logotype.assetBase = "../../../assets"`); it can't be visually verified locally since `ds-bundle/` has no `assets/` tree (see below), same limitation as Logotype itself.
- **Any other component that composes Logotype without its own assetBase override needs this same treatment** — check for `React.createElement(Logotype` / `<Logotype` usages across components (SiteFooter, SiteHeader found so far) before assuming a generated preview "just works".

## Re-sync risks

- The `http-serve.mjs` MIME-table fix above is local-only and will need reapplying (or upstreaming) every sync until the skill itself ships the fix — if a future sync shows SVG-based components suddenly failing sb-error/broken-image on both sides, check this first before treating it as a real regression. Re-applied again this sync (2026-09-03); still not upstreamed.
- Logotype's asset path fix (and now SiteFooter's/SiteHeader's) depends on the uploaded project actually carrying `assets/logo/*.svg` at its root, which is pre-existing content in this project (not produced by this skill's converter) — if that project is ever recreated fresh (e.g. synced into a brand-new empty project), `assets/` must be uploaded there too or all three will break for real. This skill's converter does not currently produce/upload an `assets/` tree — that's outside its output contract; the assets currently exist there from an earlier, separate process. Verify `assets/logo/*.svg` is present in the target project before assuming these will render correctly there. Confirmed present via `list_files` on 2026-09-03.
